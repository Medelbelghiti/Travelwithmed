### 4.0 Affiliate platform policy: only Travelpayouts-backed programs

The owner asked to keep only Travelpayouts-linked platforms active as affiliation. Applied
literally that instruction would have been destructive, and the audit script proved it before
anything was written:

```
$ npx tsx prisma/audit-affiliate-travelpayouts.ts     # read-only
  HOTELS       tp_active=0  nonTP_active=24  WOULD LOSE ALL CTAs
  FLIGHTS      tp_active=0  nonTP_active=2   WOULD LOSE ALL CTAs
  ACTIVITIES   tp_active=0  nonTP_active=24  WOULD LOSE ALL CTAs
  CAR_RENTAL   tp_active=0  nonTP_active=1   WOULD LOSE ALL CTAs
  INSURANCE    tp_active=0  nonTP_active=1   WOULD LOSE ALL CTAs
  TRAVEL_GEAR  tp_active=0  nonTP_active=1   WOULD LOSE ALL CTAs
  ESIM         tp_active=7  nonTP_active=0   OK (has TP)
```

53 active rows would have been deactivated, and 10 of the 11 confirmed programs had no
`AffiliateLink` row at all. The root cause is structural: `AffiliateLink` stored **direct**
partner URLs (Booking.com, GetYourGuide, SkyScanner, DiscoverCars), while the Travelpayouts
`tp.media` links existed only as constants in `src/lib/travelpayouts.ts`. Those links were
therefore neither migrated nor deactivatable, and the rule could not be satisfied by editing
`active` alone.

The owner approved a reconciling approach instead of the literal one. It is implemented in
`prisma/migrate-affiliate-to-travelpayouts.ts`:

| Category | Travelpayouts coverage | Result |
|---|---|---|
| `FLIGHTS` | Aviasales | 2 rows repointed, 0 direct left |
| `ACTIVITIES` | Klook / Tiqets / Go City | 24 rows repointed, 0 direct left |
| `CAR_RENTAL` | Localrent / GetRentacar | 1 row repointed, 0 direct left |
| `AIRPORT_TRANSFERS` | Kiwitaxi / Welcome Pickups / GetTransfer | no rows in DB |
| `ESIM` | Airalo / Yesim | already on `tp.media` from `fix-esim-travelpayouts.ts` |
| `HOTELS` | **none** | 24 direct rows intentionally left active |
| `INSURANCE` | **none** | 1 direct row intentionally left active |
| `TRAVEL_GEAR` | **none** | 1 direct row intentionally left active |

So every category Travelpayouts actually covers now earns Riversmag attribution, and the
categories it does not cover keep working direct partners rather than being switched off.
Passing `--deactivate-orphans` would disable the 26 `HOTELS`/`INSURANCE`/`TRAVEL_GEAR` rows and
is deliberately **not** the default, because it removes monetization with no equivalent to
replace it.

`partnerName` and `productName` are rewritten in the same transaction, so a row that used to read
`GetYourGuide - South Africa` now reads `Klook - South Africa`. Leaving the old partner name on a
repointed row would have made the admin and any partner-level reporting wrong.

```bash
# read-only coverage report
npx tsx prisma/audit-affiliate-travelpayouts.ts

# dry run, then apply
npx tsx prisma/migrate-affiliate-to-travelpayouts.ts
npx tsx prisma/migrate-affiliate-to-travelpayouts.ts --apply

# rollback from the snapshot the apply wrote to .audit/
npx tsx prisma/migrate-affiliate-to-travelpayouts.ts --rollback .audit/affiliate-tp-migration-<stamp>.json
```

Properties the script guarantees, each exercised on the disposable local cluster:

- dry run by default; writes only under `--apply`;
- one `$transaction` for the whole repoint, so there is no partially-migrated state;
- a JSON snapshot of every previous field written to `.audit/` *before* the transaction, because
  the direct-partner ids (SkyScanner `AID=7707607&PID=8058953`, GetYourGuide `partner_id=K0KEBIE`,
  DiscoverCars `a_aid=med1996`) are contractual values that cannot be reconstructed from the new
  `tp.media` URL;
- `--rollback <file>` restores `targetUrl`, `partnerName`, `productName`, `trackingParameter`, the
  UTM fields and `active` exactly;
- re-running after a successful apply reports `repoint: 0`, so it is idempotent.

**Not yet applied to production.** This ran against the local cluster only, because the Neon
credential is not available (§0.4). The same dry run, backup, apply, verify order as §4 applies.

### 4.0.0 Why "only Travelpayouts" was not applied literally — the owner's decision

The owner was offered three options and chose the reconciling one (B) over switching the 53
non-Travelpayouts rows off (C) and over leaving everything untouched (A). Recorded here so the
reasoning is not lost:

- **A** would have left the site structurally unable to satisfy the policy, because the
  `tp.media` links were not in the database at all.
- **C** would have deactivated 53 rows carrying 1 historical click between them, and left
  `HOTELS`, `FLIGHTS`, `ACTIVITIES`, `CAR_RENTAL`, `INSURANCE` and `TRAVEL_GEAR` with no CTA at
  all. The trade was real monetization for zero attributable gain.
- **B** costs nothing: the same pages keep a working link, now earning Riversmag attribution
  through Travelpayouts wherever a program exists.

The one irreversible judgement in B is that SkyScanner, GetYourGuide and DiscoverCars links were
repointed to Aviasales, Klook and GetRentacar. Those direct contracts still exist and may still
be live accounts. They held 0 clicks, so nothing was lost, and
`prisma/migrate-affiliate-to-travelpayouts.ts --rollback` restores them from the snapshot. If any
of those three direct programmes turns out to be an active revenue source, this migration should
be rolled back for that partner and the policy exception recorded here.

### 4.0.1 Two rendering guards for deactivated links

A block that stores a concrete `linkId` bypasses `resolveAffiliateLink` and therefore the
`active: true` filter every other CTA path goes through. Since `/out/[id]` redirects an inactive
link to `/`, such a block used to render a button that dumped the reader on the homepage. Two
call sites were fixed:

- `src/components/content-renderer.tsx` — an `affiliate_link` block now renders only if its link
  is active. The ids are resolved in **one batched query** before the render loop, not one query
  per block, and a database error degrades to "no affiliate CTA" rather than throwing.
- `src/app/itineraries/[slug]/page.tsx` — the same filter for `daysList[].affiliateLinks[].linkId`.

`prisma/verify-inactive-link-guards.ts` proves both against a real row by toggling `active` and
asserting render true → false → restored, and leaves the row as it found it.

**Open data-quality item, pre-existing and not introduced here:** three rows have truncated
values, `partnerName = "T"` with `productName` of `"F"` or `"A"`, across `HOTELS`, `FLIGHTS` and
`ACTIVITIES`. They were already reported in the original audit. Two were repointed by the
migration above because their category is covered; the `HOTELS` one still displays a truncated
partner name and needs a real value. This script deliberately does not invent one.


### 4.1 The 12 missing destination images (assisted, human-gated)

`seed-seo.ts` deliberately refuses to invent an image for these — an image that mislabels a
destination is a factual error. `prisma/apply-verified-images.ts` splits the work so that the
mechanical part is safe and the judgement stays human:

```bash
# 1. Source candidates: 8 per destination, with dimensions, and download them.
npx tsx prisma/apply-verified-images.ts --source

# 2. Optional but decisive: fetch the photographer's tags, which the search
#    endpoint omits. Unsplash throttles hard at ~50 calls/hour, so it stops and
#    says so rather than failing silently.
npx tsx prisma/apply-verified-images.ts --enrich

# 3. Evidence report. A candidate is VERIFIED only when the photographer's
#    geotag, tags, page slug or alt text actually names the place. Anything else
#    is reported UNVERIFIABLE, never guessed.
npx tsx prisma/apply-verified-images.ts --recommend

# 4. Open the contact sheet in a browser; it has every candidate, its evidence,
#    the best one pre-selected, and it writes the approval file for you.
start .audit\review.html

# 5. Dry run, then apply.
npx tsx prisma/apply-verified-images.ts
npx tsx prisma/apply-verified-images.ts --apply
```

### 4.2 The honesty limit on this workflow

**The agent that ran this cannot view images.** Every "verified" label in the report means the
photographer's own metadata names the place, not that a human looked at the picture. That is real
evidence of origin — a geotag reading `Chichén-Itzá, Yucatan, Mexico` is strong — but it does not
guarantee framing or subject, and a reader may still recognise a wrong landmark.

So `.audit/review.html` exists: 96 candidates, 9 pre-selected on evidence, 3 destinations with no
verifiable candidate at all (`greece`, `south-africa`, `kenya`, whose alt texts said only things
like "green trees near lake" and could have been any continent). Those three were left empty
rather than filled with a plausible guess.

Two bugs were fixed in this tool while running it, both of which had made it unable to write
anything:

- The CDN URL was built from the short Unsplash id (`d2xKRGefeWs`) instead of the canonical
  `photo-...` id embedded in `urls.regular`, producing a 404 for every candidate.
- `--source` claimed to download the review images but only wrote JSON; the old temporary
  downloader had been deleted. It now downloads and writes `review/INDEX.txt`.

The approval file is hand-edited, so a UTF-8 BOM is tolerated: PowerShell's default
`Set-Content -Encoding utf8` writes one and `JSON.parse` would otherwise reject the file.

**Unsplash attribution:** the photographer name and photo page are stored in
`.audit/image-candidates.json` for the 9 applied covers. Nothing on the site renders that credit
yet. The licence does not require it; Unsplash asks for it. Open item.

The tool refuses to write when the id is missing from the approval file, when it is one of the three
known-dead ids, when the slug does not exist, when the id was not one of our own candidates, or
when the URL does not return 200. It also reads the real pixel dimensions out of the JPEG so a
4:3-cropped card cannot be fed a portrait. Verified against the local cluster: `greece` (dead id) →
REFUSE, `atlantis` (unknown slug) → IGNORE, `portugal` (bad id) → REFUSE.
